# Contributing to qlinks

`qlinks` is both a Python package and an active scientific research codebase. Contributions
are welcome, but changes must preserve a clear distinction between stable library behaviour,
experimental algorithms, and expensive evidence-generation workflows.

## Local setup

Requirements:

- Python 3.11--3.14;
- Poetry;
- Bash or a compatible shell;
- Git and a GitHub account for pull requests.

Set up a development checkout with:

```bash
git clone https://github.com/$GITHUB_ACCOUNT/qlinks.git
cd qlinks
poetry install --with dev
```

Install optional extras only for the layer you are working on, for example:

```bash
poetry install --with dev --extras "storage drawing"
poetry install --with dev --extras "tn"
```

The tensor-network extra currently supports Python versions below 3.14.

## Before changing code

Read the repository-root `AGENTS.md`. Nested `AGENTS.md` files under `qlinks/caging`,
`qlinks/open_system`, and `experimental` add layer-specific constraints.

For nontrivial work, open or identify an issue and state:

- the scientific or software problem;
- the intended API maturity: supported, experimental, internal, or deprecated;
- the affected dependency layers;
- the intended test lane;
- any production evidence that is deliberately outside the pull-request suite.

## Making a contribution

1. Create a focused branch.
2. Make the smallest coherent change.
3. Keep scientific changes, API redesign, and unrelated cleanup in separate patches.
4. Format and lint touched code.
5. Run the narrowest relevant test, followed by the fast lane for package changes.
6. Document public API, numerical-convention, and dependency-direction changes in the pull
   request.

Typical checks are:

```bash
scripts/test.sh fast
scripts/test.sh integration
scripts/lint_blocking.sh
```

Expensive validation uses:

```bash
scripts/test.sh scientific
```

Scientific tests are not a substitute for production evidence jobs, and production evidence
jobs are not a substitute for compact regression tests.

## Review expectations

Reviewers should be able to determine:

- which mathematical or physical assumption changed;
- which code is numerical infrastructure versus scientific policy;
- which interface is intended for downstream users;
- which residual or invariant establishes correctness;
- which tests run on every pull request and which evidence is scheduled or manual.

Avoid adding package-level exports merely for convenience. Active-research objects should
normally be imported from their defining submodule until their interface has been reviewed.
