# Testing policy

`qlinks` separates fast software contracts from expensive scientific validation. The goal is
not to reduce confidence; it is to run each check at the cadence appropriate to the claim it
protects.

## Test lanes

| Lane | Purpose | Pull-request cadence |
| --- | --- | --- |
| `fast` | Tiny deterministic behavioural and algebraic contracts | Every supported Python version |
| `integration` | Small cross-module workflows on the default Python version | Every pull request |
| `scientific` | Expensive finite-size, optimization, scaling, or research-claim validation | Scheduled or manually dispatched |
| `manual` | Visual inspection or explicitly enabled diagnostics | Local only |
| `gpu` | Tests requiring a real CUDA runtime | Dedicated environment |

Bare `pytest` defaults to the fast lane. Run an explicit lane with:

```bash
scripts/test.sh fast
scripts/test.sh integration
scripts/test.sh scientific
scripts/test.sh all
```

Additional pytest arguments can follow the lane:

```bash
scripts/test.sh fast tests/caging/test_support.py -x
scripts/test.sh integration tests/caging/test_tensor_network.py -k quimb
```

The fast lane collects tests without `integration`, `scientific`, `manual`, or `gpu`. Existing
unmarked tests therefore remain in the fast baseline while the taxonomy is introduced
incrementally.

## Classification rules

Use `@pytest.mark.integration` when a test crosses package layers, exercises an optional
backend, or runs a complete numerical workflow rather than one compact contract.

Use `@pytest.mark.scientific` when the selected system size, optimization, repeated sampling,
or cross-size comparison exists to protect a scientific conclusion. Scientific tests should
normally also be integration tests, either through a module-level marker or an explicit second
marker.

A test is not a unit test merely because it lives under `tests/`. In particular, the following
belong outside the fast lane:

- production-size exact diagonalization;
- tensor-network optimization or finite-cluster scaling;
- distributed jobs;
- long stochastic trajectories or large ensembles;
- evidence-generation workflows;
- tests whose main purpose is reproducing a manuscript figure or thermodynamic trend.

## Test design

Prefer tests of public behaviour and mathematical invariants. Do not mirror every private
function with a corresponding test. Private helpers may be tested directly when they implement
a subtle standalone invariant, but their names and decomposition are not compatibility
contracts.

Every randomized test must use an explicit seed. Numerical assertions should state tolerances
that follow from the algorithm and scale, rather than adopting a larger tolerance after a
failure.

Scientific tests should include a docstring or nearby comment describing:

1. the claim being protected;
2. why a smaller system would not exercise that claim;
3. the expected runtime class and optional dependencies;
4. the residual, trend, or acceptance criterion.

## CI organization

The pull-request workflow uses separate jobs:

- one coverage-bearing fast job on the repository's default Python;
- a no-coverage fast compatibility matrix on all supported Python versions;
- a small integration job on the default Python;
- an optional tensor-network backend job on Python 3.13.

The scientific workflow is scheduled and can also be started manually. It should report slow
cases through pytest duration output and must not be required for ordinary formatting or API
patches.

## Test-health guardrail

The maintained qualitative audit lives at `tests/TEST_HEALTH_AUDIT.md`. A lightweight static
and collection-time snapshot can be generated with:

```bash
python tools/test_health.py
python tools/test_health.py --check
```

The budget in `tests/test_health_budget.json` is intentionally small in scope. It prevents
known structural debt from growing silently: direct imports of private qlinks symbols, giant
test files, unused globally registered fixtures, unmarked manual-visual cases, and accidental
loss of integration/scientific/manual markers. Update a budget only when the corresponding
architecture or testing decision is deliberate and documented.

Broadly reusable fixtures may live under `tests/fixtures/`. Fixtures specific to one scientific
area should live in the nearest `conftest.py`, so unrelated tests do not acquire ambient fixture
names.

Warnings whose origin is qlinks code are promoted to errors in pytest. Tests that intentionally
exercise an expected qlinks warning should use `pytest.warns(...)`; do not globally suppress a
new warning merely to keep the lane quiet.
