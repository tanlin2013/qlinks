# Coding and design standard

This project follows PEP 8 and PEP 257, with Black and isort configured to a 100-character
line length. The repository-root `AGENTS.md` is the authoritative source for architecture,
API maturity, testing, and scientific-review rules.

## Readability

- Prefer descriptive names over unexplained abbreviations.
- Short mathematical names are acceptable when they match the paper or a clearly stated
  formula, but document their domain and normalization.
- Keep numerical kernels separate from orchestration, reports, plotting, and serialization.
- Use typed data classes or small protocols at layer boundaries rather than broad dictionaries
  with undocumented keys.
- Raise contextual errors instead of returning sentinel arrays that can be mistaken for valid
  numerical results.

## Module organization

The package is intentionally hierarchical. New modules should live in the narrowest subpackage
that owns their responsibility; they should not be placed flatly at the package root.

A new module does **not** require a one-to-one mirror test module, and a new function does
**not** require a one-to-one mirror test method. Tests should protect behaviour, mathematical
invariants, failure modes, and supported compatibility contracts.

Large modules must not become default destinations for new work. When a change introduces a
new responsibility, extract a focused module and retain compatibility imports only when a
supported interface requires them.

## Public interfaces

An object exported from a package-level `__init__.py` is treated as a reviewed interface.
Experimental reports, intermediate search objects, and implementation helpers should remain in
their defining modules until there is a deliberate API decision.

Deprecations require:

1. a documented replacement;
2. a warning or migration note when practical;
3. a bounded set of public compatibility tests;
4. a planned removal release or milestone.

Do not preserve private implementation structure as a compatibility promise. Compatibility
facades introduced during refactoring are temporary: active package code must use the
replacement modules directly, and the facade should be removed once the replacement API is
stable and first-party callers have migrated.

## Numerical code

- Use explicit dtypes where precision or sparse representation matters.
- State random seeds in tests and evidence jobs.
- Keep basis ordering, sector conventions, and normalization explicit.
- Explain tolerance choices in terms of algorithmic error, conditioning, and system scale.
- Distinguish exact certification from floating-point verification and heuristic evidence.
- Avoid materializing dense matrices when the intended workflow is sparse, except in small
  validation cases.

## Automated checks

Blocking checks include Black, isort, flake8, and the fast pytest lane. Mypy, security scans,
and dead-code reports may remain advisory while the existing codebase is brought into
compliance.

See `docs/contributing/5.-testing.md` for test classification and commands.
